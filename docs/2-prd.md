## 1. 프로젝트 개요

### 목적

인증된 사용자가 자신만의 할일을 카테고리별로 등록·관리·조회할 수 있는 개인 할일 관리 웹 애플리케이션을 제공한다.

### 배경

- 직장인의 업무·개인 할일을 하나의 도구로 체계적으로 관리할 수 있는 전용 서비스 부재
- 사용자 인증 기반으로 개인 데이터를 안전하게 분리 저장하는 환경 필요
- 카테고리 단위 분류 및 다양한 조건 필터링 기능에 대한 수요

## 2. 타겟 사용자

| 항목 | 내용 |
|------|------|
| **주요 연령대** | 20대 ~ 50대 |
| **직군** | 직장인 |
| **사용 환경** | PC 웹 브라우저, 모바일 웹 브라우저 |
| **핵심 니즈** | 업무 및 개인 할일을 카테고리로 구분하고 간편하게 관리 |

### 페르소나 예시

- **직장인 A (30대)**: 업무 태스크와 개인 약속을 한 곳에서 관리하고, 마감일 기준으로 우선순위를 파악하고 싶다.
- **직장인 B (40대)**: PC와 스마트폰 모두에서 동일한 할일 목록을 확인하고 완료 처리하고 싶다.

## 3. 기능 요구사항

### 3.1 MVP 범위 (1차 릴리즈)

1차 릴리즈에서 도메인 정의서의 유스케이스 전체 및 추가 유스케이스(UC-14)를 구현한다.

#### 사용자 인증

| UC-ID | 기능 | 상세 요구사항 | 관련 BR |
|-------|------|-------------|--------|
| UC-01 | 회원가입 | 이메일 + 비밀번호로 가입. 이메일 중복 불가. 비밀번호 암호화 저장 (bcrypt) | BR-01 |
| UC-02 | 로그인 | 이메일 + 비밀번호 인증. JWT Access Token 및 Refresh Token 발급 | BR-01 |
| UC-03 | 로그아웃 | 클라이언트 측 토큰 제거 | BR-01 |
| UC-04 | 개인 정보 수정 | 이름, 비밀번호 수정 가능. 비밀번호 변경 시 현재 비밀번호 확인 필요 | BR-07 |
| UC-14 | 회원 탈퇴 | 본인 확인(비밀번호 재입력) 후 계정 삭제. 연관 데이터(카테고리, 할일) 즉시 전체 삭제 | BR-07 |

#### 카테고리 관리

| UC-ID | 기능 | 상세 요구사항 | 관련 BR |
|-------|------|-------------|--------|
| UC-05 | 카테고리 등록 | 인증된 사용자가 사용자 정의 카테고리 생성 | BR-05 |
| UC-06 | 카테고리 수정 | 사용자 정의 카테고리명 수정. 기본 카테고리는 수정 불가 | BR-04, BR-05 |
| UC-07 | 카테고리 삭제 | 사용자 정의 카테고리 삭제. 기본 카테고리는 삭제 불가 | BR-04, BR-05 |

> **기본 카테고리**: 시스템이 제공하는 공통 카테고리 (예: 일반, 업무, 개인)

> **카테고리 삭제 정책**: 삭제 대상 카테고리에 속한 할일이 존재하는 경우, 해당 할일은 기본 카테고리 "일반"으로 자동 이동된다. 사용자에게 이동 사실을 안내 메시지로 고지한다.

#### 할일 관리

| UC-ID | 기능 | 상세 요구사항 | 관련 BR |
|-------|------|-------------|--------|
| UC-08 | 할일 등록 | 제목(필수), 카테고리(필수), 설명(선택), 종료예정일(선택) 입력 | BR-02, BR-03 |
| UC-09 | 할일 수정 | 제목, 설명, 카테고리, 종료예정일 수정 가능. 본인 소유만 수정 가능 | BR-02 |
| UC-10 | 할일 삭제 | 본인 소유의 할일만 삭제 가능 | BR-02 |
| UC-11 | 할일 완료 처리 | 완료 여부 토글 (완료 ↔ 미완료). 본인 소유만 처리 가능 | BR-02 |
| UC-12 | 할일 목록 조회 | 카테고리 / 종료예정일 기간 / 완료 여부 기준 필터링 지원. 기본 정렬: 등록일시 내림차순 | BR-02, BR-06 |
| UC-13 | 할일 상세 조회 | 할일의 전체 정보 조회. 본인 소유만 조회 가능 | BR-02 |

### 3.2 입력값 유효성 검증 규칙

#### 사용자 (User)

| 필드 | 검증 규칙 |
|------|----------|
| 이메일 | 필수. RFC 5322 이메일 형식. 최대 255자. 시스템 내 중복 불가 |
| 비밀번호 | 필수. 최소 8자. 영문자·숫자 각 1자 이상 포함. 최대 64자 |
| 이름 | 필수. 최소 1자. 최대 50자 |

#### 카테고리 (Category)

| 필드 | 검증 규칙 |
|------|----------|
| 카테고리명 | 필수. 최소 1자. 최대 30자. 동일 사용자 내 중복 불가 |

#### 할일 (Todo)

| 필드 | 검증 규칙 |
|------|----------|
| 제목 | 필수. 최소 1자. 최대 100자 |
| 설명 | 선택. 최대 1,000자 |
| 카테고리 | 필수. 본인 소유 또는 기본 카테고리만 선택 가능 |
| 종료예정일 | 선택. 오늘 이후 날짜만 허용 (등록 시 기준) |

### 3.3 2차 릴리즈 (후순위)

| 기능 | 설명 |
|------|------|
| OAuth 소셜 로그인 | Facebook, Google 등 소셜 계정 연동 인증 |
| 다크 모드 | UI 테마 전환 |
| 다국어 지원 | 한국어 외 언어 지원 (i18n) |

## 4. 비기능 요구사항

### 4.1 성능

| 항목 | 목표 |
|------|------|
| 동시 접속자 수 | 최대 300명 |
| API 응답 시간 | 일반 요청 기준 평균 500ms 이하 |
| 서비스 규모 | 소규모 개인 프로젝트 수준 |

### 4.2 보안

| 항목 | 내용 |
|------|------|
| 인증 방식 | JWT (Access Token + Refresh Token) |
| Access Token 만료 | 1시간 |
| Refresh Token 만료 | 7일. 만료 시 재로그인 필요 |
| Refresh Token 저장 | Zustand 메모리 저장 (페이지 새로고침 시 소멸, 재로그인 필요) |
| 비밀번호 저장 | bcrypt 해시 암호화 (salt rounds: 10 이상) |
| 데이터 격리 | 사용자는 자신의 할일 및 카테고리에만 접근 가능. API 레벨에서 소유권 검증 필수 |
| 향후 확장 | OAuth 2.0 소셜 로그인 (Google, Facebook 등) — 구조 설계 시 확장성 고려 필요 |

### 4.3 데이터 정책

| 항목 | 내용 |
|------|------|
| 탈퇴 시 데이터 처리 | 회원 탈퇴 즉시 User, Category(사용자 정의), Todo 전체 삭제 |
| 개인정보 보호 | 비밀번호 평문 저장 금지 |

### 4.4 가용성 및 운영

- 소규모 개인 프로젝트로, 별도의 SLA 목표 없음
- 단일 서버 환경 운영 가능

| 항목 | 기술 |

| 항목 | 기술 |
|------|------|
| 런타임 | Node.js |
| 프레임워크 | Express |
| API 방식 | REST API |
| DB 연동 | `pg` 라이브러리 (필수) |

> **제약**: PostgreSQL DB 연동 코드는 반드시 `pg` 라이브러리를 사용해야 한다. ORM(Prisma, Sequelize 등) 사용 불가.

### 5.3 데이터베이스

| 항목 | 기술 |
|------|------|
| DBMS | PostgreSQL 17 |

### 5.4 인증

| 단계 | 방식 |
|------|------|
| 1차 | JWT (Access Token + Refresh Token 자체 발급) |
| 2차 (예정) | OAuth 2.0 소셜 로그인 (Google, Facebook 등) |

## 7. 출시 계획

### 7.1 우선순위 정의

| 우선순위 | 기능 |
|----------|------|
| **P0 (필수)** | 회원가입, 로그인, 로그아웃, 회원 탈퇴 |
| **P0 (필수)** | 할일 등록, 수정, 삭제, 완료 처리, 목록 조회 |
| **P1 (중요)** | 카테고리 등록·수정·삭제, 할일 상세 조회, 개인정보 수정 |
| **P2 (후순위)** | OAuth 로그인, 다크 모드, 다국어 지원 |

### 7.2 개발 일정 (1차 MVP — 3일)

#### Day 1: 프로젝트 셋업 + 인증

| 시간대 | 작업 | 산출물 |
|--------|------|--------|
| 오전 | 프로젝트 초기 세팅 (디렉토리 구조, 패키지 설치, 환경변수 구성) | 실행 가능한 빈 프로젝트 |
| 오전 | DB 스키마 설계 및 테이블 생성 (User, Category, Todo) | DDL SQL, 기본 카테고리 시드 데이터 |
| 오후 | 백엔드: 회원가입·로그인·로그아웃·회원 탈퇴 API (UC-01, UC-02, UC-03, UC-14) | `/auth`, `/users/me` REST API |
| 오후 | 프론트엔드: 회원가입 / 로그인 화면, JWT 토큰 관리 | 인증 UI + Zustand 인증 상태 |

#### Day 2: 카테고리 + 할일 핵심 기능

| 시간대 | 작업 | 산출물 |
|--------|------|--------|
| 오전 | 백엔드: 카테고리 CRUD API (UC-05, UC-06, UC-07) | `/categories` REST API |
| 오전 | 백엔드: 할일 등록·수정·삭제·완료 처리 API (UC-08, UC-09, UC-10, UC-11) | `/todos` REST API |
| 오후 | 프론트엔드: 카테고리 관리 UI | 카테고리 목록·등록·수정·삭제 화면 |
| 오후 | 프론트엔드: 할일 등록·수정·삭제·완료 처리 UI | 할일 폼·카드 컴포넌트 |

#### Day 3: 조회·필터링 + 개인정보 수정 + QA

| 시간대 | 작업 | 산출물 |
|--------|------|--------|
| 오전 | 백엔드: 할일 목록 조회(필터링·정렬) · 상세 조회 API (UC-12, UC-13) | 필터링 쿼리 파라미터 지원 |
| 오전 | 백엔드: 개인정보 수정 API (UC-04) | `/users/me` REST API |
| 오후 | 프론트엔드: 할일 목록(필터 UI) · 상세 조회 화면 | 필터 컴포넌트 + 상세 모달/페이지 |
| 오후 | 프론트엔드: 개인정보 수정 · 회원 탈퇴 화면 | 프로필 편집 UI |
| 오후 | 통합 테스트 · 버그 수정 · 반응형 UI 점검 | 배포 가능한 MVP |

## 8. 제약사항 및 가정

| 구분 | 내용 |
|------|------|
| **기술 제약** | DB 연동은 `pg` 라이브러리만 사용 (ORM 금지) |

| **가정** | 할일 공유·협업 기능은 범위 외 |

## 9. 용어 정의

| 용어 | 정의 |
|------|------|
| **사용자 (User)** | 회원가입 후 인증을 통해 앱을 사용하는 주체 |
| **할일 (Todo)** | 사용자가 등록한 단위 작업 항목 |
| **카테고리 (Category)** | 할일을 분류하는 그룹 단위. 기본 카테고리와 사용자 정의 카테고리로 구분 |
| **기본 카테고리** | 시스템이 제공하는 공통 카테고리. 사용자가 수정·삭제 불가 |
| **사용자 정의 카테고리** | 인증된 사용자가 직접 생성한 카테고리 |
| **종료예정일 (Due Date)** | 할일을 완료해야 하는 목표 날짜 |
| **완료 여부 (Completion Status)** | 할일의 진행 상태 (완료 / 미완료) |
| **MVP** | Minimum Viable Product — 1차 출시를 위한 최소 기능 집합 |
| **JWT** | JSON Web Token — 서버 세션 없이 클라이언트가 토큰으로 인증하는 방식 |
| **반응형 웹** | 화면 크기에 따라 레이아웃이 자동 조정되는 웹 UI |
